# RepostGuard-Lite

> **English** | [中文](README_Chinese.md)

RepostGuard-Lite is an AIGC image binary-classification research project for social-platform reposting, editing, and compression scenarios. In addition to comparing single-branch RGB/semantic baselines, the project studies the fusion of semantic features with frequency-domain and residual forensic features, and evaluates generalization under strict unseen-generator tests and multi-stage perturbations.

The current primary experimental version is **Community Forensics train-v3**. On the complete 4,000-image strict unseen-generator test set, M2 achieves **0.9308 Clean AUROC** and **85.78% Accuracy**; under the six-stage random combined perturbation, its AUROC is **0.8525**. M2 is therefore preferred for the **current train-v3 deployment objective**, with B2 retained as a complementary baseline for ranking difficult generators. M3, however, should not be dismissed as ineffective: it consistently outperformed M2 in the more data- and generator-constrained SID-Set and train-v2 settings, so it is better understood as a candidate fusion strategy whose value depends on training-set scale and diversity.

For everyday on-device use, Jiang Xinshuo (`@8309`) further completed the M2/M3-to-Student distillation experiments. The selected final model, **V3.2.1** (formerly V3.2 corrected), compresses the parameter count to **7.96M** (approximately **8.00%** of M3) and achieves **0.9063 Clean AUROC** on the same 4,000-image expanded strict-unseen test set. Its FP32 ONNX/TorchScript exports, ONNX Runtime parity records, fully offline Galaxy S23 Ultra Android demo source, test APK, and blind-test image pack have all been released. Standardized on-device latency, power, and peak-memory measurements remain outstanding.

> This repository does not include the original data, and the M2/M3 teacher weights are not committed directly to Git. The train-v3 M2/M3 `safetensors` weights, verified through tensor-by-tensor consistency checks and remote re-download validation, are publicly available on Hugging Face; see [Public Model Weights](#public-model-weights-hugging-face) for download and inference instructions. Reproducing training still requires reacquiring the data from the manifests and preserving the `resolved_config.yaml` generated by each run. To support mobile review, completed Student distillation checkpoints, ONNX/TorchScript exports, and per-sample evaluation artifacts are stored separately in [`student_distillation/`](student_distillation/).

### 1. Install Weight Download and Loading Dependencies

First complete the project setup in [Installation and Environment](#installation-and-environment), then install the following packages in the same virtual environment:

```bash
python -m pip install "huggingface-hub>=1,<2" "safetensors>=0.4,<1"
```

### 2. Download a Pinned Version

The commands below use unambiguous full commit SHAs rather than `main`, which may change later. If the virtual environment is active, use `hf` directly. Otherwise, replace it with `.venv/bin/hf` on macOS/Linux or `.venv\Scripts\hf.exe` in Windows PowerShell.

```bash
hf download LLL640/RepostGuard-Lite-M2-train-v3 \
  --revision 06e2ca759f69b48cb50ea81a581b6f1ce8a94317 \
  --local-dir models/repostguard-m2-train-v3

hf download LLL640/RepostGuard-Lite-M3-train-v3 \
  --revision 1b0588638ace3664cc51d571d9675c43f1a3ac68 \
  --local-dir models/repostguard-m3-train-v3
```

After downloading, verify the release files in the corresponding model directory. macOS uses `shasum`; Linux typically uses `sha256sum`:

```bash
cd models/repostguard-m2-train-v3
shasum -a 256 -c SHA256SUMS.txt
```

### 3. Run Inference on a Real Image

The repository includes the standalone [`scripts/infer_hf_image.py`](scripts/infer_hf_image.py) script, which strictly reuses the project RGB handling, bicubic resize, Q90 JPEG format-debiasing, and model tensor-conversion logic. To run M2:

```bash
python scripts/infer_hf_image.py \
  --model-dir models/repostguard-m2-train-v3 \
  --image /path/to/image.jpg \
  --device cpu
```

To run M3, change only `--model-dir` to `models/repostguard-m3-train-v3`. NVIDIA systems may use `--device cuda`. A runtime message stating `No pretrained weights loaded` is expected: the code first constructs the network with `load_pretrained=False`, then immediately loads the complete Hugging Face state dict with `strict=True`. The reported `aigc_score` is a sigmoid ranking score, not a calibrated authenticity probability for the target deployment domain. The table thresholds were selected only on the train-v3 internal validation set; deployment to a new platform or device requires a separate calibration set and a newly selected threshold.

## Project Overview

### Research Questions

General AIGC detectors can easily learn shortcuts tied to file formats, encoders, or seen generators. Real platform images also undergo resizing, cropping, JPEG compression, blur, noise, color adjustment, and repeated re-encoding. The project therefore focuses on four questions:

1. Can a detector generalize to exact generators absent from training, or even to unseen generator architecture families?
2. What do conventional augmentation, frozen vision-language features, and forensic feature fusion each contribute to reposting robustness?
3. Does the per-sample dynamic gating in M3 provide a stable benefit over the direct fusion used by M2?
4. Can teacher distillation compress M2/M3 into a Student that runs entirely on-device while keeping performance loss on strict unseen generators within an acceptable range?

### Model Architectures

| Model | Architecture and training differences | Total parameters | Trainable parameters |
|---|---|---:|---:|
| B0 | ImageNet-pretrained EfficientNet-B0 + Dropout(0.2) + binary linear head; clean-only baseline | 4,008,829 | 4,008,829 |
| B1 | Architecturally identical to B0; adds only symmetric robustness augmentation during training data loading | 4,008,829 | 4,008,829 |
| B2 | Frozen OpenCLIP ViT-B/32 `laion2b_s34b_b79k` + 512→1 linear head | 87,849,729 | 513 |
| M2 | Frozen CLIP semantic branch + DCT/SRM/NPR forensic branch + feature-fusion classifier | 99,423,442 | 11,574,226 |
| M3 | M2 + two-branch dynamic gating conditioned on a 6-dimensional quality descriptor | 99,423,744 | 11,574,528 |
| Student V3.0 | MobileNetV3-Large; logits/KD distillation with M3 as the only teacher | 4,203,313 | 4,203,313 |
| Student V3.2.1 | MobileNetV3-Large semantic branch + EfficientNet-B0 lightweight forensic/NPR branch; adds feature/forensic/gate distillation | 7,955,038 | 7,955,038 |

M2/M3 were inspired by [AIDE](https://arxiv.org/abs/2406.19435) ([official implementation](https://github.com/shilinyan99/AIDE)) and retain its core idea of combining high-level semantic evidence with low-level forensic evidence, but they are not direct reproductions of AIDE. M2 uses a shared lightweight forensic encoder together with NPR-inspired residuals, attention-based patch aggregation, and original/degraded-image consistency training, shifting the research focus toward robustness to real reposting under a limited parameter budget. M3 extends M2 to study quality-conditioned dynamic branch fusion.

![RepostGuard-Lite M2/M3 model architecture](reports/assets/model_architecture/repostguard_m2_m3_architecture.svg)

The M2 forensic branch divides a 224×224 image into 16 patches of 56×56. DCT processing selects 2 low-frequency and 2 high-frequency groups and combines them with RGB, 30-channel SRM responses, and 3-channel NPR residuals. A 1×1 adapter, a ResNet-18 trained from scratch, type embeddings, and attention pooling produce a 256-dimensional forensic representation, which is fused with a projected 256-dimensional CLIP representation.

M3 adds a `LayerNorm(6) → Linear(6,32) → GELU → Linear(32,2) → Softmax` gate on top of M2. The final layer is zero-initialized, so training begins with equal weighting of the two branches. M3 has only 302 more parameters than M2; the difference is the fusion strategy, not model capacity.

#### Parameter Scale, Competition Constraint, and On-Device Potential

The [TikTok TechJam 2026](https://tiktoktechjam2026.devpost.com/) challenge documentation states: **"Participants must use models with <2B parameters."** M2/M3 are counted using total model parameters, including the frozen OpenCLIP backbone, rather than trainable parameters alone:

| Model | Total parameters | Billions of parameters | Share of 2B limit | Trainable parameters |
|---|---:|---:|---:|---:|
| M2 | 99,423,442 | 0.099423B | 4.971% | 11,574,226 |
| M3 | 99,423,744 | 0.099424B | 4.971% | 11,574,528 |

Both models are below **0.1B**, approximately one twentieth of the competition's 2B limit, and clearly satisfy the `<2B` requirement. Dynamic gating adds only 302 parameters to M3 relative to M2. Freezing most of the semantic backbone and training only about 11.57M parameters also lowers retraining and task-adaptation cost. M2/M3 are therefore reasonable starting points for lightweight edge deployment and could be further compressed through FP16/INT8 quantization, structured pruning, ONNX/Core ML/TensorRT export, and operator fusion. Meeting the parameter limit does not mean that on-device deployment is complete: model file size, peak memory, latency, throughput, power consumption, and backend compatibility of the DCT/SRM/NPR operators must still be measured on the target phone or edge hardware before claiming device readiness.

Student distillation addresses this bottleneck by transferring the fused knowledge of the large models into mobile-friendly architectures. The 4.20M-parameter V3.0 is only **4.23%** of M3 (approximately **23.65×** smaller), while the 7.96M-parameter V3.2.1 is **8.00%** of M3 (approximately **12.50×** smaller). V3.2.1 has been exported to approximately **31.3 MB** FP32 ONNX and TorchScript, passed ONNX Runtime parity, and been integrated into a fully offline Galaxy S23 Ultra Android demo. This demonstrates a functioning delivery path, but not completed production-grade on-device performance validation.

### Training Method

All train-v3 models are trained independently, without continuing from CIFAKE or SID-Set detector checkpoints. Public pretrained weights are used only for the EfficientNet or OpenCLIP backbones.

- Input: RGB, 224×224.
- Training: 3 epochs, AdamW, cosine scheduler, 5% warm-up, AMP, gradient clipping=1.
- B0/B1: batch size 128, learning rate `3e-4`.
- B2: batch size 96, learning rate `1e-3`, weight decay `1e-5`.
- M2/M3: batch size 24, gradient accumulation 2, effective batch size 48, learning rate `2e-4`.
- Checkpoint selection: internal-validation Clean AUROC only.
- Decision threshold: frozen using internal-validation balanced accuracy only; external test labels are not used for model or threshold selection.
- Format debiasing: data loading applies a consistent RGB conversion, bicubic resize, and same-class, same-parameter JPEG round trip. Training randomly selects quality factors 70/80/90/95, while evaluation fixes Q90; no second image dataset is generated.

The paired M2/M3 objective consists of clean BCE, degraded BCE, symmetric Bernoulli KL, and cosine feature consistency:

```text
L = BCE(clean) + BCE(degraded)
  + 0.50 * symmetric_KL
  + 0.25 * cosine_inconsistency
```

## Datasets and Evaluation Protocol

### Dataset Version Evolution

| Version | Training data | Primary purpose | Subsequent status |
|---|---:|---|---|
| CIFAKE pilot | 10k train + 2k val; 32×32; a single SD1.4 synthetic source | Validate the B0/B1/B2/M2 code path | Retained only as a low-resolution pipeline pilot; original data and checkpoints were removed |
| SID-Set pilot | 20k train + 4k val; one indivisible AIGI generator/style domain | Introduce M3, load-time format debiasing, and strict combined perturbations | Completed only same-source validation; original data and checkpoints were removed |
| Community Forensics train-v1 | 18k, with 9k each of Real/AIGI | First multi-source Community Forensics baseline | Current `main` no longer provides a standalone v1 training entry point |
| train-v2 | 20k, with 10k each of Real/AIGI | Promote all 2k images from the former external seen-family set into training | The seen-family set is no longer permitted as a test set |
| train-v3 | 24k, with 12k each of Real/AIGI | Add 1k GAN, 1k pixel diffusion, and a balanced 2k Real sample | Current primary training set |

train-v3 contains **921 exact AIGI generator labels**. New AIGI samples come from CommunityForensics-Small and aim to broaden exact-subcategory coverage for GAN and pixel diffusion; new Real images are sampled evenly under two corresponding 1,000-image quotas. Because the pinned Small revision records every Real source as `N/A`, no stronger claim of balanced Real source categories can be made. train-v3 is not a single-variable experiment relative to v2: sample count, generator coverage, Real sampling quotas, and the sampling seed all changed.

### Why the Project Moved from CIFAKE and SID-Set to Community Forensics

The official submission requires retaining the CIFAKE and SID-Set pilots, but their primary role is to validate the training, evaluation, and robustness pipelines rather than demonstrate real deployment generalization.

#### CIFAKE Pilot: Low-Resolution and Single-Generator Shortcuts

The CIFAKE pilot uses 10,000 official training images and 2,000 official test images as validation, with an exactly balanced Real/AIGI split. Every image is a **32×32 JPEG**, and AIGI images come only from **Stable Diffusion 1.4**. Upscaling 32×32 images to 224×224 cannot restore lost texture, edge, or spectral detail. Strong blur, resizing, or JPEG perturbations also affect such natively low-resolution images much more than typical social-media images. Models can therefore exploit shortcuts tied to a single generator style or low-resolution statistics, limiting practical value.

| Model | Clean AUROC | Clean BAcc | Mean AUROC over 17 perturbations | Mean BAcc over 17 perturbations | Worst AUROC |
|---|---:|---:|---:|---:|---:|
| B0 | **0.9945** | **0.9705** | 0.8638 | 0.7448 | 0.5442 |
| B1 | 0.9929 | 0.9570 | **0.9730** | **0.9043** | **0.9120** |
| B2 | 0.9738 | 0.9220 | 0.9202 | 0.7693 | 0.7688 |
| M2 | 0.9904 | 0.9545 | 0.9641 | 0.8986 | 0.8971 |

Every Clean AUROC exceeds 0.97, but the worst B0 AUROC is only 0.5442. This contrast shows that high same-source Clean performance does not establish reposting robustness and cannot establish effectiveness on new generators. M3 had not yet been implemented during the CIFAKE pilot, so it has no corresponding result.

See [`reports/historical/INITIAL_RESULTS.md`](reports/historical/INITIAL_RESULTS.md) for the complete CIFAKE condition table and run boundaries.

#### SID-Set Pilot: Higher Resolution but Insufficient Style/Generator Domains

The SID-Set pilot uses 20,000 official training images and 4,000 official validation images, retaining only the Real and full-synthetic classes. It addresses CIFAKE's low-resolution limitation, but the metadata available to this project does not identify the exact generators of full-synthetic images; every AIGI sample is recorded as `sid-set-full-synthetic-unspecified`. Here, "single-style generator" means that **the pilot contains only one auditable, indivisible AIGI style/generator domain**. It is not a claim that the full official SID-Set dataset was generated by exactly one underlying model.

This setup makes it easy for models to fit the visual style, content distribution, or generation process shared by training and validation instead of robustly learning the local detail and spectral anomalies that distinguish AIGI from Real images. The raw data also has a strong format correlation: nearly all Real images are JPEG/MPO, while all AIGI images are PNG. Although the project applies the same JPEG round trip to both classes during loading, historical compression traces and same-source style cannot be removed completely.

| B0 | **0.999950** | **0.997000** | 0.953356 | 0.904941 | 0.469849 | 0.718696 | 0.510750 |
| B1 | 0.999933 | **0.997000** | **0.999559** | **0.992221** | 0.997098 | **0.991335** | **0.937750** |
| B2 | 0.998484 | 0.982250 | 0.996342 | 0.938912 | 0.984164 | 0.936252 | 0.618250 |

Training and validation, however, come from the same SID-Set source and lack independent exact-generator labels, so the high AUROC cannot be interpreted as evidence of real unseen-generator generalization.

#### Research Basis and Principles for the Small Community Forensics Build

[Park and Owens, *Community Forensics: Using Thousands of Generators to Train Fake Image Detectors* (CVPR 2025)](https://openaccess.thecvf.com/content/CVPR2025/html/Park_Community_Forensics_Using_Thousands_of_Generators_to_Train_Fake_Image_CVPR_2025_paper.html) show that generator diversity in the training data is an important constraint on generalization to unseen generators. In their controlled experiments, increasing only the number of training generators while holding the total number of training images fixed still improves detection across multiple test-generator architectures, especially for out-of-distribution categories such as pixel diffusion and GAN. In other words, adding more images from the same generator does not substitute for adding generator diversity.

The official Community Forensics dataset contains approximately 2.7 million images and 4,803 generators and occupies about 1.08 TB. Even the Small version is too large for direct training under this project's single-GPU, job-duration, and 100 GB Home quota constraints. The project therefore does not download or train on the full dataset; instead, it constructs a traceable small version:

1. Pin the Hugging Face revision, manifest, random seed, and source locator, and materialize only selected images.
2. train-v1 uses 900 exact AIGI generators in 18,000 training images, with 10 images per generator, prioritizing generator diversity over repeated sampling from the same source.
3. train-v2 incorporates 9 additional exact generators and their images, expanding the set to 20,000 images.
4. train-v3 adds 1,000 GAN images, 1,000 pixel diffusion images, and 2,000 corresponding Real images, reaching 24,000 images, a 12,000/12,000 Real/AIGI split, and 921 exact AIGI generators.
5. AIGI sampling covers as many subcategories as possible and keeps each exact generator's contribution as even as possible within the same quota. Image-level SHA-256 and pHash audits prevent train-test leakage.

The corresponding strict unseen-generator test set does not merely hold out random images; it holds out both generator architecture families and exact identities absent from training. The current 4,000-image test set contains 2,000 AIGI and 2,000 Real images. Its AIGI side covers 12 untrained commercial/other generators, including DALL·E, Adobe Firefly, FLUX, Ideogram, Imagen, Midjourney, and Stable Cascade; its Real side covers COCO, FFHQ, LAION, and RAISE. It is closer than same-source CIFAKE/SID-Set validation to the practical problem of detecting future unknown commercial generators after platform processing, but it still does not represent every future generator or real traffic distribution.

| M3 | 0.9210 | 0.9132 | **0.8888** | 0.8489 | 0.9154 | 76.15% |

B1 and B0 have identical architectures and parameter counts. Their Clean results are nearly identical (0.8117 vs 0.8125), but the six-stage AUROC rises from 0.6597 to 0.7435, showing that the main value of training augmentation appears under compound degradation rather than Clean ranking.

### External Exact-Seen and Difficult Generators

External exact-seen Clean AUROC: B0 0.7933, B1 0.7999, B2 0.8114, M2 0.8558, and M3 0.8578. **B2 has the highest equally weighted Clean macro-AUROC across the three difficult generators, at 0.7261**; it also has the highest equally weighted Clean macro-AUROC across all five external slices, at 0.7521.

This does not make B2 the best overall model. It is substantially weaker than M2/M3 on the full strict unseen set but ranks Hourglass, DFGAN, and GALIP more reliably, exposing generator-specific blind spots in the current semantic-forensic fusion models. The three difficult slices share the same Real negative panel, so they are correlated diagnostics rather than three statistically independent populations.

### Fair train-v2 versus train-v3 Intersection Comparison

The comparison uses only the 2,000 image IDs shared by the v2/v3 strict unseen test sets and fixes the same 21 conditions:

| Model | Clean AUROC v2→v3 | Change | Mean non-Clean v2→v3 | Change |
|---|---:|---:|---:|---:|
| B0 | 0.8199→0.8199 | -0.0000 | 0.7480→0.7531 | +0.0050 |
| B1 | 0.8204→0.8152 | -0.0051 | 0.7657→0.7848 | +0.0191 |
| B2 | 0.7632→0.7641 | +0.0009 | 0.7635→0.7680 | +0.0044 |
| M2 | 0.9191→0.9252 | +0.0061 | 0.8994→0.9107 | +0.0112 |
| M3 | 0.9279→0.9261 | -0.0018 | 0.9082→0.9109 | +0.0027 |

The mean non-Clean result improves for all five models, but only two Clean point estimates improve, and the Clean confidence intervals include zero. This supports the statement that data expansion generally improves perturbation robustness, but the change cannot be attributed to any single added data factor. On the same train-v2 strict unseen intersection, M3 versus M2 achieves 0.9279 vs 0.9191 Clean AUROC and 0.9082 vs 0.8994 mean non-Clean AUROC. Under train-v3, the corresponding results become 0.9261 vs 0.9252 and 0.9109 vs 0.9107, so the relative M3 advantage has nearly converged.

### M3 Dynamic-Gate Ablation

Four inference modes are compared using the same M3 checkpoint on the complete 4,000-image strict unseen set under 21 conditions:

| Gate mode | Clean AUROC | Clean Accuracy | Mean non-Clean AUROC | 6-stage AUROC |
|---|---:|---:|---:|---:|
| Learned per-sample gate | 0.930533 | 85.35% | 0.915381 | 0.848941 |
| Fixed to the Clean-set mean gate | 0.930264 | 85.43% | **0.915464** | 0.848951 |
| Gate randomly shuffled across samples | 0.930452 | 85.43% | 0.915289 | **0.849029** |
| Fixed 0.5 / 0.5 | 0.929502 | 85.40% | 0.914846 | 0.848065 |

The learned gate exceeds the fixed mean gate by only 0.000269 Clean AUROC and the randomly shuffled gate by only 0.000081; the fixed mean gate is slightly better on mean non-Clean AUROC. This ablation supports only the following conclusion: **under the expanded train-v3 data setting and this checkpoint**, per-sample gating does not provide a stable, practically meaningful aggregate gain. It does not imply that dynamic gating is ineffective under every training-data setting. The learned global share of approximately 58.8% semantic / 41.2% forensic may still be useful, but computing a fixed mean gate from the test-input distribution is a diagnostic only, not a deployable method.

### Interpreting M3 Gating Across Dataset Scales

Smaller or less generator-diverse training settings provide different evidence from train-v3:

| Training setting and same-protocol test | M2 | M3 | M3−M2 |
|---|---:|---:|---:|
| SID-Set validation (historical pilot) Clean AUROC | 0.998046 | 0.999744 | +0.001698 |
| SID-Set validation (historical pilot) mean AUROC over 17 perturbations | 0.996126 | 0.999402 | +0.003276 |
| SID-Set validation (historical pilot) worst-condition AUROC | 0.988386 | 0.998147 | +0.009761 |
| SID-Set validation (historical pilot) six-stage AUROC | 0.961302 | 0.975617 | +0.014315 |
| SID-Set validation (historical pilot) six-stage balanced accuracy | 0.684500 | 0.739000 | +0.054500 |
| train-v2 strict unseen Clean AUROC | 0.9191 | 0.9279 | +0.0088 |
| train-v2 strict unseen mean over 20 non-Clean conditions | 0.8994 | 0.9082 | +0.0088 |
| train-v2 4-stage A / 4-stage B / 6-stage AUROC | 0.8968 / 0.8631 / 0.8276 | 0.9087 / 0.8732 / 0.8328 | +0.0119 / +0.0101 / +0.0052 |

The interpretation most consistent with all experiments is therefore: **M3 has an advantage in smaller, more homogeneous data settings or when branch reliability differs more strongly; as train-v3 increases sample diversity and volume, M2 learns a fusion representation of nearly equal effectiveness, reducing the marginal benefit of per-sample M3 gating.** This is a working hypothesis supported by cross-dataset results, not a causally verified conclusion. The SID-Set values come from a historical pilot on the same validation split and establish only relative performance within that setting, not external unseen-generator generalization. In addition, SID-Set and train-v2 M2/M3 models were trained independently with a single seed, so the observed gains cannot all be attributed to the 302 added gate parameters. The most direct next step is to reproduce fixed, mean, and shuffled gate ablations on the train-v2 M3 checkpoint, then compare M2/M3 with shared initialization and multiple seeds across controlled ladders of dataset scale and generator diversity.

### Student Distillation and Mobile Experiments

This phase was led by team member **Jiang Xinshuo (`@8309`)**. The goal was not to enlarge the teacher networks further, but to transfer the semantic and forensic discrimination learned by the stronger M2/M3 models into lightweight Students, making AIGI detection suitable for phones, offline privacy-sensitive scenarios, and fast everyday checks. Student input remains 224×224 RGB, normalization is embedded directly in the model, and the model outputs one AIGI logit. The device does not need to upload the original image or call a cloud inference service.

The experiments converged through the following sequence:

| Version | Teacher and method | Student parameters | Key findings and artifacts |
|---|---|---:|---|
| [V1](student_distillation/v1_m2_30_m3_70/) | M2 30% + M3 70%; MobileNetV3-Large; hard/KD/consistency=`0.5/0.4/0.1`, T=3 | 4,203,313 | First dual-teacher distillation; internal 18-condition Clean/robust mean AUROC of 0.9753/0.9642; includes ONNX and TorchScript |
| [V3.0](student_distillation/v3_first_m2_0_m3_100/) | M3-only; MobileNetV3-Large; T=3 | 4,203,313 | Clean/robust mean/worst AUROC of 0.8784/0.8490/0.7931 on expanded V3 unseen 4k; approximately 16.8 MB ONNX/TorchScript; ONNX parity passed |
| [V3.1 T=3](student_distillation/v3_1_t3_baseline/) | M3-only; 19-family holdout baseline | 4,203,313 | Family-unseen development Clean/robust mean AUROC of 0.7919/0.7552; no mobile export |
| [V3.1 T=1](student_distillation/v3_1_t1_diagnostic/) | Changes only the KD temperature from 3 to 1 | 4,203,313 | Clean AUROC 0.7837, below T=3; temperature is not the only issue; no comparable robustness evaluation or mobile export completed |
| [V3.2.1](student_distillation/v3_2_1/) | M3-only; corrects sampling and teacher calibration and adds a lightweight forensic branch plus feature/forensic/gate distillation | 7,955,038 | Substantially exceeds V3.1 on family-unseen development; Clean/robust mean/worst AUROC of 0.9063/0.8711/0.8127 on protected expanded V3 unseen 4k; includes ONNX, TorchScript, parity, Android source, APK, and blind-test image pack |

The V1/V3.0 internal validation and V3.1/V3.2.1 family-unseen development sets use different protocols, so internal high scores cannot rank versions across those groups. The comparison below includes only models evaluated on the same expanded strict-unseen 4k manifest (SHA-256 `59ca2e4c...`) with the same 21-condition perturbation matrix (SHA-256 `69531f3f...`); each model uses a threshold selected on its own internal validation set. V3.2.1 uses a different training manifest from M2/M3/V3.0, so the table compares end-to-end deployment candidates rather than a single-factor distillation ablation.

| Model | Parameters | Relative to M3 | Clean AUROC | Clean balanced accuracy | Robust mean AUROC | Robust mean balanced accuracy | Worst AUROC |
|---|---:|---:|---:|---:|---:|---:|---:|
| M2 teacher | 99,423,442 | 100.00% | **0.9308** | **0.8578** | **0.9163** | 0.8370 | **0.8525** |
| M3 teacher | 99,423,744 | 100.00% | 0.9305 | 0.8535 | 0.9154 | **0.8381** | 0.8489 |
| Student V3.0 | 4,203,313 | 4.23% | 0.8784 | 0.8030 | 0.8490 | 0.7745 | 0.7931 |
| **Student V3.2.1** | **7,955,038** | **8.00%** | **0.9063** | **0.8105** | **0.8711** | **0.7328** | **0.8127** |

Among the Students, V3.2.1 has the strongest ranking performance. Relative to the M3 teacher, its Clean AUROC is **0.0242** lower, robust mean AUROC is **0.0443** lower, and worst AUROC is **0.0363** lower, while parameter count falls by approximately **92.0%**. Threshold-metric losses are larger: Clean balanced accuracy is **4.30 percentage points** lower and robust mean balanced accuracy is **10.53 percentage points** lower. Separate calibration and target-device-domain threshold selection therefore remain mandatory before deployment; AUROC alone cannot establish full equivalence to the teacher model.

The V3.2.1 [`student_mnv3_fp32.onnx`](student_distillation/v3_2_1/mobile/student_mnv3_fp32.onnx) and [`student_mnv3_fp32.torchscript.pt`](student_distillation/v3_2_1/mobile/student_mnv3_fp32.torchscript.pt) have both been delivered. ONNX Runtime parity passed with a maximum probability error of `0.000427231` and a maximum gate error of `0.000653714`. [`android/RepostGuardDemo/`](android/RepostGuardDemo/) provides a fully offline Android demo with English as the default and optional Simplified Chinese localization; it requests no Internet or storage permissions. The test APK, 30-image blind-test pack, and installation guide are in [`student_distillation/v3_2_1/android/`](student_distillation/v3_2_1/android/). This delivery is intended for Galaxy S23 Ultra testing and does not replace a production-grade security audit or standardized on-device latency/throughput, peak-memory, and power benchmarks.

The V3.2.2 full refit restored the 19 families and 2,004 samples previously used for family-unseen development to the complete 24,000-row training manifest and used an independent 1,500-image validation set. This diagnostic trained through epoch 10: the best checkpoint occurred at epoch 1 (AUROC **0.726831**), and performance declined to **0.628780** by epoch 10. It therefore stopped at the gate and did not continue to epoch 20. The frozen V3.2.1 epoch-3 model remains the formal evidence/release model. Complete checkpoints, per-sample predictions, run cards, audits, and reproducibility boundaries are documented in [`student_distillation/README.md`](student_distillation/README.md).

## Local Directory Inference (Original `.pt` Training Checkpoints)

This batch-inference entry point targets original `.pt` checkpoints from local training. It recursively reads common image formats from a directory and outputs an AIGC score for every readable image. The safe Hugging Face release packages contain only `model.safetensors`; use the [real-image inference example](#3-run-inference-on-a-real-image) above for public weights. The original batch entry point requires both files from the same training run:

```text
<MODEL_DIR>/
├── best.pt
└── resolved_config.yaml
```

The program strictly checks the configuration summary to prevent checkpoint/configuration mismatches. Original `.pt` weights are not committed to Git by default; download public M2/M3 inference weights from the Hugging Face repositories above. Do not store Hugging Face access tokens in this repository.

Linux/macOS example:

```bash
.venv/bin/python -m repostguard.infer \
  --config /path/to/model/resolved_config.yaml \
  --checkpoint /path/to/model/best.pt \
  --input-dir /path/to/images \
  --output predictions.json \
  --diagnostics diagnostics.json \
  --batch-size 16 \
  --device cpu
```

Windows PowerShell example:

```powershell
.\.venv\Scripts\python.exe -m repostguard.infer `
  --config C:\path\to\model\resolved_config.yaml `
  --checkpoint C:\path\to\model\best.pt `
  --input-dir C:\path\to\images `
  --output predictions.json `
  --diagnostics diagnostics.json `
  --batch-size 16 `
  --device cpu
```

Use `--device cuda` on Windows/Linux systems with an NVIDIA GPU. Output is a standard JSON array:

```json
[
  {"image_path": "example.jpg", "pred": 0.9342},
  {"image_path": "subdir/image.png", "pred": 0.1276}
]
```

`image_path` is relative to the input directory. `pred` is the sigmoid model score, not a real probability calibrated for the deployment domain. Corrupt or unreadable images are omitted from the primary output, with detailed reasons recorded in the diagnostics file; results are written through atomic temporary-file replacement.

## Reproducing the Experiments

### 1. Pin Code, Data, and Protocol

1. Clone the code and record the commit SHA.
2. Pin the Hugging Face revision, sampling seed, and manifest SHA256 according to the data manifest.
3. Strictly preserve the role boundaries among internal validation, exact-seen, hard-generator, and strict unseen sets.
4. Do not use external/hard test labels to tune the model, select a checkpoint, or choose a threshold.

Recommended data-dependency order:

```text
base 24k
  ├─ internal validation / legacy external manifests
  └─ validation-v2 3k
       └─ train-v2 promotion
            ├─ train-v3 additions
            └─ expanded strict-unseen v3
```

The completion markers, in order, are `COMPLETE`, `VALIDATION_V2_COMPLETE`, `TRAIN_V2_COMPLETE`, `TRAIN_V3_COMPLETE`, and `EXTERNAL_UNSEEN_V3_COMPLETE`. A completed download log alone does not establish that the full data chain is complete.

### 2. Train B0/B1/B2/M2/M3

The train-v3 configurations are in [`configs/community_forensics_v3/`](configs/community_forensics_v3/). Train B0, B1, B2, M2, and M3 independently in that order, preserving:

- `best.pt`;
- `resolved_config.yaml`;
- the internal-validation selection metric and frozen threshold;
- the Git commit, data-manifest SHA256, random seed, and run logs.

Complete commands for data construction, training, robustness evaluation, and report generation on the current cluster are in [`README_slurm.md`](README_slurm.md). That file also records TC2 compute-node constraints, resource settings, logs, and recovery procedures.

Important reproducibility boundaries:

- The base Community Forensics training configurations on the current `main` branch already target train-v2 and cannot directly retrain historical train-v1. Restore the historical v1 lineage from commit `76cf99a` in an isolated worktree and re-audit current resource settings.
- During a clean rebuild, the base data wrapper may chain into model training before validation-v2/train-v2 is complete. Use separate data-stage scripts and dependencies, or implement a data-only switch first; the current process must not be described as an unconditional one-command rebuild.
- The Home quota is 100 GB. Selected images occupy approximately 35 GB, and the Hugging Face cache and intermediate state require additional space; check quota before downloading.
- If raw files have been deleted, do not retain stale SQLite state and assume that resumption is safe. The manifest, raw objects, and completion markers must agree.

### 3. Fixed Evaluation

Evaluate each model with the same manifest, perturbation matrix, and frozen threshold:

1. External exact-seen 2k.
2. Hard Hourglass, DFGAN, and GALIP, 500 each.
3. Full strict unseen-generator 4k.
4. Clean, the 17 original perturbations, two 4-stage combinations, and one 6-stage combination.
5. Output per-image predictions, per-condition metrics, summary, configuration summary, and manifest summary.

Cross-version comparisons must use the intersection of image IDs and conditions. Do not compare the v2 2k strict unseen set directly with the complete v3 4k strict unseen set and attribute the difference to training-data changes.

### 4. Generate and Verify Reports

Reports should include at least AUROC, AP, Accuracy, Precision, Recall, Specificity, F1, MCC, balanced accuracy, and low-FPR TPR, with each metric identified as either ranking performance or a frozen-threshold operating point. HTML/Markdown reports must be traceable to per-image predictions and the manifest rather than preserving charts alone.

Cluster reproductions must not run Python, training, inference, or tests directly on the Head Node. Submit all computation through non-interactive batch jobs. Details and copyable commands are in [`README_slurm.md`](README_slurm.md).

## Limitations and Next Steps

1. **Single random seed.** Current core conclusions rely mainly on one training run. Add at least 3–5 seeds and report means, variances, and paired confidence intervals.
2. **v2→v3 is not a single-factor change.** Sample count, generator categories, Real-source quotas, and seed all changed. The next step is factor-by-factor incremental and quota-matched experiments.
3. **Unseen domains remain limited.** The strict unseen set contains only 12 exact generators and 4 Real sources; it cannot represent every commercial model, open model, camera, or content domain.
4. **Difficult-generator blind spots.** M2/M3 are substantially weaker than B2 on Hourglass, DFGAN, and GALIP. Branch-feature conflicts, source-domain sampling, and hard-negative training require further study.
5. **Insufficient low-FPR performance and calibration.** M2/M3 have high AUROC, but TPR@1%FPR is 0 on the current complete unseen set. Use an independent calibration set, temperature scaling/isotonic regression, and larger tail samples.
6. **Incomplete format debiasing.** A consistent JPEG round trip does not cover EXIF, color spaces, denoising, screenshots, proprietary social-platform encoders, or repeated-upload history.
7. **The value of M3 gating is data-dependent.** M3 consistently outperforms M2 on SID-Set and train-v2, but fixed/shuffled gate ablations on train-v3 show that the per-sample benefit nearly disappears. Future work should use shared initialization, multiple seeds, and the same-checkpoint ablations across controlled ladders of dataset scale and generator diversity to separate the effects of gating, random training differences, and data coverage. Consider fixed fusion only if marginal gains remain absent under large, diverse datasets.
8. **The data-rebuild engineering path still needs consolidation.** Add a true data-only entry point, end-to-end manifest rehydration, content-hash deduplication, and COCO/DALL-E holdout auditing.
9. **Deployment-domain shift.** Current tests use a 50% class prior, and scores are not probability-calibrated for the deployment domain. Production use requires re-estimating thresholds, false-positive costs, and drift on the target platform.
10. **On-device performance is not yet a reproducible hardware benchmark.** V3.2.1 has approximately 31.3 MB FP32 ONNX/TorchScript exports, passed parity, and includes fully offline Android demo source and a test APK. Dual-branch compute, preprocessing, activation memory, and device backends still affect speed, power, and stability. Standardized Galaxy S23 Ultra latency/throughput, peak-memory, power, and quantization benchmarks are required before confirming a deployment tier.

With more time, the priority order is: multi-seed retraining → M3 dataset-scale/diversity ladder ablations → low-FPR calibration → targeted difficult-generator diagnostics → factorial data ablations → fully recoverable one-command data construction → validation through real reposting chains on target platforms.
